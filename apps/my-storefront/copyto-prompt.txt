This structure explainedbelow represents the gold standard for multi-vendor marketplace architecture. By choosing **item/fulfillment-item status as the sole authoritative source of truth**, you eliminate state desynchronization bugs (such as a vendor marked "Delivered" while an underlying item is still "Processing").
## 1. The Authoritative Bottom-Up State Engine
rule—"Fulfillment Item --> Vendor fulfillment status --> Order fulfillment status"—
[ Line Item / Fulfillment Item ]  <-- AUTHORITATIVE SOURCE OF TRUTH
               │
               ▼  (Rollup Engine)
    [ Vendor Partition Status ]
               │
               ▼  (Rollup Engine)
    [ Overall Order Status ]

### State Rollup Rules Matrix

| Item-Level Statuses in Partition         | Derived Vendor Status       | Derived Order Status |
| ---                                      |                   ---       |                  --- |
| All items `NOT_FULFILLED`                | `PROCESSING` | `PROCESSING` |
  `PROCESSING` 
| Some items `SHIPPED`,                    | `PARTIALLY_SHIPPED`         | `PARTIALLY_FULFILLED` |
  some `PROCESSING`
| All items in Vendor                      | Vendor A: `SHIPPED`         | `PARTIALLY_FULFILLED` |
  A `SHIPPED`, Vendor B `PROCESSING        | Vendor B: `PROCESSING`     | 

| All items across ALL vendors `DELIVERED` | Vendor A: `DELIVERED`       | `FULFILLED` / `DELIVERED` |
                                             Vendor B: `DELIVERED`
| Some items `DELIVERED`, some `CANCELED`  |`PARTIALLY_DELIVERED`       | `PARTIALLY_FULFILLED` |

## 2. Structural Continuum Across the Customer & Platform Journey

By preserving the `Vendor Partition` wrapper at every point in the lifecycle, the user experience remains predictable and smooth:

CART                       CHECKOUT                   CUSTOMER ORDER             PLATFORM ADMIN
┌─────────────────────┐    ┌─────────────────────┐    ┌─────────────────────   ┐    ┌─────────────────────┐
│ Vendor A            │    │ Vendor A            │    │ Order #1001          │    │ Order #1001       │
│  ├── Item A         │    │  ├── Item A         │    │  ├── Vendor A          │    │  ├── Customer       │
│  └── Item C         │    │  ├── Item C         │    │  │   ├── Item A (Ship) │    │  ├── Payment        │
│ Subtotal: ₹...      │    │  └── Shipping A     │    │  │   └── Item C (Del)  │    │  └── Vendors (2)    │

## 3. Why This Architecture Wins

1. **Unified Checkout, Distributed Logistics:**
* The customer experiences a **single authorization & payment collection** at checkout (one credit card transaction or UPI payment).
* Internally, the order breaks into clean vendor partitions with dedicated shipping quotes per vendor.
2. **Granular Package Tracking:**
* Vendors ship independently. Product A can have `Tracking: XXX1` (Delivery via BlueDart) while Product B from another seller has `Tracking: XXX2` (Delivery via Delhivery).
3. **Decoupled Vendor Actions:**
* Vendor A fulfilling or refunding Item A does not block or modify Vendor B’s fulfillment pipeline or force lock states on the parent Order entity.
4. **Resilient Financial Ledger:**
* Split payments, commissions, and vendor payouts naturally bind to the vendor partition layer, matching Medusa v2’s payment collection model.
